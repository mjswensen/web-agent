# Agent instructions for Web Agent

## Start here

1. Read [`CONTEXT.md`](./CONTEXT.md) for the repository map and current implementation notes.
2. Check [`README.md`](./README.md) and `package.json` for supported usage and verification commands.
3. Inspect the existing module and adjacent tests before editing.

## Architecture

- Keep one `Bun.serve` server, one `/ws` endpoint, and exactly one in-process `AgentSessionRuntime`. Never add a Pi subprocess, fallback transport, or second runtime.
- Keep the SDK runtime owner, command adapter, RPC broker, WebSocket handling, Git provider, and client reducer separate.
- Use only public `@earendil-works/pi-coding-agent` APIs. Keep the dependency pinned exactly.
- Preserve loopback and port-fallback defaults. Browser frames and SDK records are untrusted; validate them and do not enable permissive CORS.
- External extensions, package resources, themes, image input, telemetry, and model-catalog network refreshes are intentionally disabled.
- Restrict persisted session listing and replacement to the launch project.

## React and client state

- Use React functional components and hooks (`useState`, `useEffect`, `useContext`, `useSyncExternalStore`).
- Keep mutable state app-scoped through `AppState` and React context; never create a mutable module singleton.
- Access `window`, `document`, and `WebSocket` only in browser lifecycle code.
- Keep transforms/reducers pure and reconnect snapshots authoritative. Render structured messages with stable IDs, separate thinking from assistant text, and sanitize Markdown HTML.

## Browser RPC contract

- Preserve browser IDs and send command responses only to the originating tab. Broadcast live events and snapshots to all tabs.
- Keep stream batching near 16 ms. Retain only the newest cumulative tool update per `toolCallId`; flush errors and lifecycle/session/terminal events immediately.
- A prompt response is emitted when SDK preflight accepts it, not after the model turn completes.
- Permit only one new/switch/fork/clone transition at a time.

## UI and styling

- Follow the responsive shell and use Tailwind's default palette and the monospace visual language.
- Controls need accessible labels, semantic elements, visible focus states, and 44-by-44 CSS-pixel targets for critical actions.
- Never render untrusted Markdown/HTML directly. Preserve whitespace safely for tool output and diffs.

## Editing and verification

- Use `functions.read`, precise `functions.edit`, and `functions.write` only for new files or full rewrites.
- Keep `.js` extensions in server-relative imports. Add focused tests beside changed implementation.
- Do not edit `build/` as source. `src/server/embedded-assets.generated.ts` is generated by `scripts/embed-client.ts` during build.
- Formatting is Prettier: tabs, single quotes, no trailing commas, 100 columns.
- Never add credentials or tests requiring real providers.

```sh
bun run check
bun run lint
bun run test:unit
bun run test:e2e
bun run build
```

For production changes, verify the compiled executable from an empty directory with clean `HOME`, restricted `PATH`, `PI_OFFLINE=1`, and no adjacent assets or `node_modules`.

Before finishing, confirm loopback remains default, no undocumented shell/filesystem command was added, exactly one SDK runtime exists, and docs reflect user-facing or architectural changes.
